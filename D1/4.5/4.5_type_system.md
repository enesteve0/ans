# 4.5 Type System

*Citing Sebesta Ch. 6.*

ANS is a small statically typed domain-specific language whose type system is
shaped by two requirements stated in §4.1: compile-time validation of chemistry
(every formula symbol resolves, every `check = balanced` reaction conserves
atoms) and a surface syntax that mirrors textbook chemistry. The type system
therefore mixes general-purpose primitive types with a small set of fixed
domain-specific types (Element, Compound, Reaction, Formula, Quantity) and
deliberately avoids user-defined type constructors.

---

## Primitive Types and Their Value Sets

ANS recognises five primitive (scalar) types. Each value's surface syntax is
determined by the lexer (§4.2); the semantic phase fixes its type.

| Type | Surface syntax | Value set |
|---|---|---|
| **Number** | `NUMBER_LITERAL` (e.g. `20`, `1.008`, `6.02e23`) | IEEE-754 double-precision floating-point values. There is no separate Integer type — `20` and `20.0` denote the same value. |
| **String** | `STRING_LITERAL` (e.g. `"Water"`) | Finite sequences of Unicode characters between double quotes, with the escape set `\" \\ \n \r \t`. |
| **Character** | `CHAR_LITERAL` (e.g. `'H'`, `'\n'`) | Single Unicode characters in single quotes, with the same escape set. |
| **Boolean** | *no literal surface syntax* | The two values produced by `==`, `!=`, `<`, `<=`, `>`, `>=`, and used as the condition of `if` / `elif`. Stating §4.2's deferred note: ANS does not define `true` / `false` keywords; booleans have run-time values but no literal source form, so a `let b = (1 < 2)` binding is the only way to name one. Boolean is *not* a valid typed-parameter annotation — `<type_name>` in the grammar is restricted to `element`, `compound`, and `reaction` — so Boolean exists only as an intermediate value type carried by `let` bindings and condition expressions. |
| **Quantity** | `<number_literal> <unit>` (e.g. `5.0 mol`, `890.3 kJ/mol`) | Pairs of a Number and one of the units `mol`, `g`, `kg`, `kJ`, `g/mol`, `kg/mol`, `kJ/mol`. Quantities are primitive scalars in Sebesta's sense — they have no addressable internal components — but they carry a unit tag used for compile-time dimension tracking. |

In addition, ANS has four built-in structured / domain types: **Formula** (an
ordered map from element symbol to non-negative integer count, see §4.4),
**List** (heterogeneous, see below), and the three declared kinds **Element**,
**Compound**, and **Reaction**. These are described under "Structured Types".

---

## Strong Typing (Sebesta §6.12)

By Sebesta's working definition (§6.12), a language is strongly typed when every
type error is detected — either at compile time or at run time — and when there
are no implicit conversions that silently lose information. **ANS is strongly
typed.** Three properties carry the argument:

1. **Static type rules for typed names.** Every element, compound, and reaction
   has a declared kind fixed at its declaration site. Typed function parameters
   (`reaction r`, `compound c`, `element e`) are checked at the call site: passing
   the compound `water` to a `reaction r` parameter is a compile-time error, not
   a silent reinterpretation.
2. **Run-time checks for `let` bindings.** Untyped `let` variables and untyped
   function parameters do still receive types — each value carries its type at
   run time, and every operator and built-in checks the operand type
   (`formula[E]` requires `E` to be an Element, §4.4; arithmetic requires
   Numbers or compatible Quantities). A mismatched operand raises
   `semantic_error` or a run-time type error rather than being coerced.
3. **No silent dimension or kind loss.** A `kJ/mol` Quantity cannot be added to
   a plain Number, and a Formula cannot be compared with a String. Both are
   rejected outright; neither is implicitly demoted.

The price is the one Sebesta flags in §6.12: a few constructs defer the type
check from compile time to run time. The clearest case is heterogeneous lists.
Because a `let mixed = [1, "two", water]` declaration mixes types, the element
type of `mixed` is not known statically, and an operation on `mixed[i]` or on
the loop variable of `for (let item in mixed) { … }` is checked **at run time**
against the value's type tag. A `mixed[i].atomic_mass` access where `mixed[i]`
turns out to be a Number raises a run-time type error rather than being
silently coerced. ANS accepts this trade because heterogeneous lists are a
writability feature for the chemistry domain (mixing compounds, formulas, and
counts in one collection), and Sebesta's strong-typing criterion is preserved
as long as the check still happens — which it does.

## Implicit Type Coercion (Sebesta §7.4)

ANS performs **essentially no** implicit coercions. There is only one numeric
type, so `20` and `20.0` are the same Number value and mixed arithmetic such
as `2 * 0.5` is not a coercion at all — it is a single-type operation. Two
cases that might appear to be coercions are actually not:

1. **Integer-shaped literals are already Numbers.** `20` and `20.0` denote the
   same IEEE-754 value; no conversion is performed because no second numeric
   type exists.
2. **Stoichiometric coefficients are plain Numbers, not coerced Quantities.**
   The `2` in `2*O2` (§4.4) is parsed as `<number_literal>` by the grammar
   and is used directly as a scalar multiplier in atom-map arithmetic
   (`2 * { O: 2 } = { O: 4 }`). It is *not* promoted to a unitless Quantity —
   reaction-expression arithmetic is defined over (Number, Formula) operands,
   not over Quantities.

Explicitly **disallowed** coercions, which other languages perform but ANS
rejects outright:

- Number ⇄ String (no `"5" + 3`),
- Character ⇄ String (a `'H'` is not a one-letter `"H"`),
- Element ⇄ Formula (`H` the element and `H` the formula are different — the
  semantic checker promotes `H` to a Formula only inside species position),
- Quantity ⇄ Quantity across units (`5 g` and `5 kg` are not interconverted
  implicitly; a future `convert()` built-in would be explicit).

The motivation follows §7.4: every avoided implicit coercion is a class of
reliability bugs avoided in chemistry calculations, where a missing factor of
1000 between `g` and `kg` is the bug that matters most.

## Type Equivalence (Sebesta §6.14)

ANS uses **name equivalence** for all named types (Element, Compound, Reaction,
the typed function parameter annotations) and **structural equivalence** for
the two anonymous structured types, Formula and Quantity.

- **Name equivalence for nominal kinds.** Two values have the same type only
  when their declarations carry the same kind keyword (`element`, `compound`,
  `reaction`). Two distinct `compound` declarations with identical fields are
  still different compounds — `compound water { formula = H2O, name = "Water" }`
  and `compound dihydrogen_monoxide { formula = H2O, name = "Water" }` are not
  interchangeable. This matches Sebesta's argument in §6.14 that name
  equivalence preserves *intent*: the programmer who wrote two declarations
  meant two distinct entities.
- **Structural equivalence for Formula and Quantity.** Two formulas are equal
  when their atom-count maps are equal (this is exactly the rule that lets
  `check = balanced` work in §4.4); two quantities are equal when both their
  numeric value and their unit tag match. There is no notion of a "named
  formula type", so structural is the only sensible rule.

The choice is forced by the language goals. Name equivalence is easy to
implement, makes chemistry error messages refer to the user's declared names
(`expected compound, got reaction combustion`), and aligns with the static
scoping argument of §4.6: every name resolves textually to a single
declaration, and that declaration *is* its type identity.

## Structured Type Design Decisions (Sebesta §6.5–6.7)

ANS exposes two general-purpose structured types and three domain-specific
record-like aggregates. Each is described against Sebesta's design-decision
checklist.

### List (Sebesta §6.5 — array category)

```ans
let elements = [H, O, C];
let list = [1, "two", 3.45, water, methane.formula];
```

| Sebesta design decision | ANS choice |
|---|---|
| Element type | **Heterogeneous.** Any value, of any type, may appear in the same list. Each element carries its own run-time type tag. |
| Index type and range | **Number, 0-based,** with range `0..length-1`. |
| Indexing result type | **Determined at run time** from the stored element's type tag. `list[0]` has no static type; subsequent operations on the result (e.g. `list[0].atomic_mass`) are type-checked against the actual tag at run time, consistent with the strong-typing argument above. |
| Subscript bounds check | **Always checked at run time.** An out-of-range index raises a run-time error; there is no unchecked indexing mode. |
| Allocation category (§6.5.2) | **Heap-dynamic,** with size fixed at creation. There is no `push` / `pop` in Part 1, so the list is closer to Sebesta's *fixed heap-dynamic* than to a fully dynamic array. |
| Initialisation | **Always at declaration** via the list literal `[ … ]`. Uninitialised lists do not exist. |
| Slices | Not supported. |

A list is *not* an aggregate of homogeneous chemistry values; it is a general
collection. Domain-specific aggregates use the record-like declared kinds
described next.

### Record-like Declared Types (Sebesta §6.7)

Element, Compound, and Reaction are ANS's record types. They are not declared
with a general `record { … }` constructor; each kind has a fixed schema fixed
at language design time:

| Kind | Required fields | Field types |
|---|---|---|
| `element <Symbol> { … }` | `atomic_mass`, `valence`, `symbol` | Number, Number, String |
| `compound <name> { … }` | `formula`, `name` | Formula, String |
| `reaction <name> { … }` | `reactants`, `products`, `check`, `energy` | ReactionSide, ReactionSide, balance-tag, Quantity |

A **ReactionSide** is the runtime type produced by evaluating a
`<reaction_expression>` such as `CH4 + 2*O2`. Its representation is the
atom-count map built by `reaction_atoms(R)` in §4.4 — a map from element
symbol to Number — together with the original parsed term list so that the
side can be printed back in the user's original form. It is not exposed as a
declarable type and not accepted as a `<type_name>` parameter annotation; it
exists only as the type of the `reactants` and `products` fields. The
`balance-tag` field type has exactly one inhabitant, the contextual keyword
`balanced`, and the `energy` field is a Quantity restricted by §4.4 to units
`kJ` or `kJ/mol`.

Following Sebesta §6.7, every record has:

- **A fixed field set.** Each schema lists exactly the required fields; missing
  or duplicate fields are semantic errors (§4.4).
- **Named field access by dot.** `water.formula`, `combustion.products`,
  `H.atomic_mass`. There is no positional access.
- **No nesting beyond the schema.** A compound contains a Formula; a Formula is
  itself structured but is not user-extensible. Free user-defined records are
  not supported in Part 1.

### Formula (Sebesta §6.5 — associative-array view)

Formula values are also structured but are accessed as associative arrays:
`formula[H]` returns the count of `H` in the formula, and `for (let element in
formula)` iterates over the formula's first-appearance element order (§4.4).
This is the only ANS type whose indexing operator returns a Number even though
indexing semantically looks like field access in a record.

---

The overall result is a type system that is small, mostly static, and tuned to
the chemistry domain: nominal types and dimension-tagged quantities catch the
errors that chemistry students actually make, while a single heterogeneous
List and a Number-only numeric model keep writability close to textbook
notation.
