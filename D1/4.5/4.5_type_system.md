# 4.5 Type System

*Citing Sebesta Ch. 6.*

ANS is a statically typed domain-specific language. Its type system is small —
four primitive types, one general structured type, and a fixed set of
chemistry domain types — and is shaped by the compile-time validation goals
of §4.1 (resolve every element symbol, balance every reaction, track every
unit).

---

## Primitive Types (Sebesta §6.2)

ANS recognises four primitive scalar types, each "not defined in terms of
other data types" in Sebesta's sense.

| Type | Surface syntax | Value set |
|---|---|---|
| **Number** | `NUMBER_LITERAL` (`20`, `1.008`, `6.02e23`) | IEEE-754 double-precision values. There is no separate Integer type; `20` and `20.0` denote the same value. |
| **String** | `STRING_LITERAL` (`"Water"`) | Finite Unicode sequences with escapes `\" \\ \n \r \t`. |
| **Character** | `CHAR_LITERAL` (`'H'`, `'\n'`) | Single Unicode characters with the same escape set. |
| **Boolean** | *no literal surface syntax* | The two values produced by `==`, `!=`, `<`, `<=`, `>`, `>=` and consumed by `if` / `elif`. ANS has no `true` / `false` keywords; Boolean is not a valid `<type_name>` annotation, so it exists only as the value type of comparison results and `let` bindings such as `let b = (1 < 2)`. |

---

## Domain Types

The remaining types are domain-specific. They are built into the language with
fixed schemas; ANS does not provide a general record or class constructor.

- **Quantity** — a pair (Number, unit), where unit is one of `mol`, `g`, `kg`,
  `kJ`, `g/mol`, `kg/mol`, `kJ/mol`. Although surface syntax is `5.0 mol`,
  Quantity is *defined in terms of* Number and a unit tag, so it is a
  structured (domain) type, not a primitive.
- **Formula** — an ordered map from element symbol to non-negative integer
  count, plus a first-appearance iteration order (§4.4). Surface syntax:
  `FORMULA_LITERAL` such as `H2O`, `CH4`.
- **List<T>** — see "Structured Type Decisions" below.
- **Element**, **Compound**, **Reaction** — record-like aggregates declared by
  the user with a fixed schema (see "Record-like Declared Types" below).
- **ReactionSide** — the type of the `reactants` and `products` fields of a
  Reaction. A ReactionSide is a list of `(coefficient, species)` terms, where
  each *species* must resolve to a declared Compound; formula literals such as
  `H2O` are accepted only when they match a declared compound. The atom-count map
  used by `check = balanced` is **derived** from a ReactionSide by the
  semantic operation `reaction_atoms` (§4.4), not its representation. A
  ReactionSide is not a declarable type and is not accepted as a `<type_name>`
  annotation.

---

## Strong Typing (Sebesta §6.14)

**ANS is strongly typed:** every type error is detected at compile time —
typed parameters and built-ins such as `mol(...)` are checked at call sites,
every formula symbol must resolve to a declared element, reaction-side formulas
must resolve to declared compounds, every `check = balanced` reaction must
conserve atoms, each `let` binding fixes its variable's type from the
right-hand side, and every list literal is checked for element-type homogeneity.
There are no
silent dimension or kind conversions — a `kJ/mol` Quantity is not addable to
a Number, a Compound is not implicitly a Formula, and a `List<Number>` is
not assignable to a `List<Compound>`. Homogeneous lists keep all element
accesses statically typed, so the type-check deferral that Sebesta flags in
§6.14 does not arise in ANS.

---

## Implicit Type Coercion (Sebesta §7.4)

ANS performs **no implicit coercions**. Cases that look like coercions are
not:

- **Integer-shaped literals** (`20` vs. `20.0`) are the same Number value;
  there is no second numeric type to convert from.
- **Stoichiometric coefficients** in `2*O2` are plain Numbers used as scalar
  multipliers on atom-map arithmetic (§4.4); they are not promoted to
  unitless Quantities.

Explicitly **rejected** cross-type uses: Number ⇄ String, Character ⇄ String,
Element ⇄ Formula, Quantity ⇄ Quantity across different units (`5 g` ↛ `5 kg`).
Each rejection eliminates a class of chemistry-calculation bug — exactly the
motivation Sebesta gives for restricting coercion in §7.4.

---

## Type Equivalence (Sebesta §6.15)

ANS uses three simple, kind-driven rules:

1. **Name equivalence for primitive and domain types.** Element, Compound,
   Reaction, Number, String, Character, Boolean, Formula are equivalent only
   when their declared type names match. Two `compound` declarations with
   identical fields — `compound water { formula = H2O, name = "Water" }` and
   `compound dihydrogen_monoxide { formula = H2O, name = "Water" }` — are
   *different* compounds, matching Sebesta's argument that name equivalence
   preserves programmer intent.
2. **Unit-tag compatibility for Quantities.** Two Quantities have the same
   type when their unit tags match exactly (`5 mol` and `7 mol` are
   compatible; `5 mol` and `7 g/mol` are not).
3. **Structural equivalence for `List<T>`.** `List<T1>` and `List<T2>` are
   the same type if and only if `T1` and `T2` are equivalent by the rules
   above. A `List<Number>` and a `List<Compound>` are different types.

This three-rule split avoids the inconsistency of treating Formula as
structural and Compound as nominal: every named kind is nominal, every
parameterised collection is structural.

## Structured Type Decisions (Sebesta §6.5–6.7)

### List<T> (Sebesta §6.5 — array category)

```ans
let elements  = [H, O, C];                       // List<Element>
let compounds = [water, methane, co2, oxygen];   // List<Compound>
```

| Sebesta design decision | ANS choice |
|---|---|
| Element type | **Homogeneous.** All elements of a list must share a single static type `T`, inferred from the list literal. A literal that mixes types — such as `[1, "two", water]` — is a compile-time type error. Although the grammar accepts `[]` as valid syntax, the semantic checker rejects a bare `[]` because no element type can be inferred from an empty literal; `List<T>` is not a valid `<type_name>` annotation, so no external context can fix `T` either. Both rejections are semantic rules, not syntactic ones. |
| Index type and range | **Number, 0-based**, range `0..length-1`. |
| Subscript bounds check | **Always checked at run time.** No unchecked indexing mode. |
| Indexing result type | **`T`** — fully static. `list[0]` has type `T`, so subsequent operations such as `list[0].atomic_mass` are checked at compile time against `T`'s fields. |
| Allocation category (§6.5.2) | **Fixed heap-dynamic** — created with size fixed at creation. No `push` / `pop` in this project. |
| Initialisation | **Always at declaration** via the list literal `[ … ]`. |
| Slices | Not supported. |

### Record-like Declared Types (Sebesta §6.7)

Element, Compound, and Reaction are ANS's records. Each kind has a fixed
schema defined at language-design time; ANS does not expose a general
`record { … }` constructor.

| Kind | Required fields | Field types |
|---|---|---|
| `element <Symbol> { … }` | `atomic_mass`, `valence`, `symbol` | Number, Number, String |
| `compound <name> { … }` | `formula`, `name` | Formula, String |
| `reaction <name> { … }` | `reactants`, `products`, `check`, `energy` | ReactionSide, ReactionSide, balance-tag, Quantity |

Each record has a **fixed field set** (missing or duplicate fields are
semantic errors, §4.4), **named field access** via dot notation
(`water.formula`, `combustion.products`), and **no user-defined nesting** — a
Compound contains a Formula because the schema says so, not because a user
nested records. Free user-defined records are not supported in ANS.

### Formula as Associative Array (Sebesta §6.6)

Formula is structured but is accessed in an associative-array-like manner
(Sebesta §6.6): `formula[element]` maps an element key to its atom count,
exactly as an associative array maps a key to a value. `for (let element in
formula)` iterates over the formula's first-appearance element order (§4.4).
It is the only ANS type whose indexing operator returns a Number from what
otherwise looks like field access.

---

The result is a small, mostly compile-time type system: four primitives, a
single parameterised collection `List<T>`, and a fixed family of chemistry
records. Strong typing, name equivalence for nominal kinds, and the absence
of implicit coercions together catch the chemistry errors that the language
exists to catch.
