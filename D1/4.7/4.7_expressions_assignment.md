# 4.7 Expressions and Assignment

*Citing Sebesta Ch. 7.*

Sebesta describes expressions as the main way a language specifies computation.
He also treats assignment as one of the central constructs of imperative
languages because assignment changes program state. For ANS, the design goal is
to keep expression evaluation predictable: precedence is explicit, operand order
is defined, coercion is not used, and assignment is kept separate from ordinary
expressions.

---

## Expression Forms

ANS expressions include literals, identifiers, arithmetic expressions,
comparison expressions, unary negation, function calls, member access, and
indexing.

```text
number literal        18.0, 6.02e23
quantity literal      5 mol, 890.3 kJ/mol
string literal        "Water"
character literal     'H'
formula literal       H2O, CH4, CO2
identifier            mass, water, formula
unary expression      -mass
binary expression     a + b, a * b
comparison            mass > 18.0, x == y
function call         molar_mass(water), mol(reactants[c])
member access         c.formula, element.atomic_mass
indexing              formula[element], list[0]
```

Built-in functions such as `mol()` follow the same call syntax as
user-defined functions. `mol(reactants[c])` extracts the stoichiometric
coefficient of compound `c` from a ReactionSide as a plain Number.

Reaction-side expressions such as `CH4 + 2*O2` are handled by the separate
reaction grammar, not by ordinary arithmetic expression rules. This avoids
overloading `+` and `*` with two unrelated meanings in the same expression
context.

---

## Precedence and Associativity

ANS uses grammar structure to define operator precedence. Higher-precedence
forms are parsed before lower-precedence forms.

| Precedence, high to low | Operators / forms | Associativity |
|---|---|---|
| 1 | Function call `()`, member access `.`, indexing `[]` | Left to right |
| 2 | Unary `-` | Applies to one operand |
| 3 | `*`, `/` | Left to right |
| 4 | `+`, `-` | Left to right |
| 5 | `==`, `!=`, `>=`, `<=`, `>`, `<` | Non-chaining |

For example:

```ans
mass + element.atomic_mass * formula[element]
```

is interpreted as:

```text
mass + (element.atomic_mass * formula[element])
```

because member access and indexing happen before multiplication, and
multiplication happens before addition.

ANS allows only one comparison operator in a comparison expression. Therefore:

```ans
a < b < c
```

is not treated as a chained comparison. The programmer must write the intended
logic explicitly in separate conditionals.

---

## Boolean Expressions and Short-Circuiting

In the current ANS grammar, comparison operators produce Boolean values, but
there are no Boolean operators such as `&&`, `||`, `and`, or `or`. Because of
that, short-circuit evaluation does not apply in the current language.

A condition in `if` or `elif` must evaluate to a Boolean value produced by a
comparison expression:

```ans
if (mass > 18.0) {
    print "high mass";
}
```

ANS does not allow numbers or strings to be used as conditions. This follows the
reliability goal from the type system: a condition must be clearly Boolean, not
accidentally truthy or falsy.

Since there are no Boolean operators, compound conditions that would require
logical AND or OR must be expressed as nested `if` statements:

```ans
// To check: mass > 18.0 AND valence == 2
if (mass > 18.0) {
    if (valence == 2) {
        print "heavy divalent element";
    }
}
```

This is a deliberate constraint: it keeps every condition a single,
unambiguous comparison rather than a compound expression that could hide
short-circuit behavior.

---

## Operand Evaluation Order

ANS defines operand evaluation order as left to right. Sebesta notes that
leaving operand order unspecified can make programs behave differently in
different implementations, especially when function calls have side effects.
ANS avoids that problem by choosing a fixed order.

For a binary expression:

```ans
a + b
```

ANS evaluates `a` first, then `b`, then applies `+`.

For a function call:

```ans
molar_mass(water)
```

ANS evaluates the arguments from left to right before entering the function.

For indexing:

```ans
formula[element]
```

ANS evaluates `formula` first, then `element`, then applies the indexing rule.

For member access:

```ans
element.atomic_mass
```

ANS evaluates `element` first, then reads the `atomic_mass` field.

## Type Rules and Coercion

ANS does not use implicit coercion. Ordinary arithmetic operators require
compatible operand types, and the Part 2 subset keeps arithmetic numeric:

```text
Number + Number -> Number
Number - Number -> Number
Number * Number -> Number
Number / Number -> Number
```

Formula indexing is a special domain-specific expression rule:

```text
Formula[Element] -> Number
```

So:

```ans
formula[element]
```

returns the number of atoms of that element in the formula.

In the Part 2 implementation subset, Quantity values appear as stored literals
only — for example, a `reaction` energy field (`890.3 kJ/mol`) or a
unit-tagged `let` variable (`let amount = 5.0 mol`). Arithmetic on Quantity
values is not defined in this subset; all computed arithmetic expressions use
Number operands. A `kJ/mol` Quantity is not addable to a plain Number, and
Quantities with different unit tags are not interchangeable:

```text
Quantity + Number               // type error
Quantity (kJ/mol) + Quantity (g/mol)  // type error — unit mismatch
Quantity (kJ/mol) + Quantity (kJ/mol) // type error — not supported in this subset
```

Even same-unit Quantity addition such as `890.3 kJ/mol + 100.0 kJ/mol` is not
supported in this subset; Quantities are stored and type-checked but not computed
with. This matches the no-implicit-coercion rule from §4.5: every unit tag is
part of the type, so mixing units is a compile-time error rather than a silent
wrong result.

ANS does not support user-defined operator overloading. Chemistry-specific
meanings, such as adding reaction species in `CH4 + 2*O2`, are kept in the
reaction grammar instead of being mixed into normal arithmetic.

## Assignment

Assignment in ANS is a statement, not an expression:

```ans
mass = 18.0;
```

This statement updates `mass`, but it does not produce a value. Therefore, ANS
rejects expression-style assignment such as:

```ans
x = y = 3;       // invalid
if (x = 3) { }   // invalid
```

This avoids the common confusion between assignment `=` and equality comparison
`==`.

Assignment targets are restricted by the grammar. A target must start with an
identifier and may then use member access or indexing. This means assignment
targets are not general expressions, even though they reuse some postfix syntax.

```text
identifier
identifier.field
identifier[index]
identifier.field[index]
```

Not every syntactically valid target is semantically writable. The semantic
checker rejects targets that do not denote a mutable storage location:

```text
Writable locations:
  let variables              mass = 18.0;     valid
  list elements              list[0] = water;  valid

Non-writable locations:
  element / compound / reaction fields   c.formula = H2O;      invalid
  formula atom counts                    formula[element] = 2;  invalid
```

Element, Compound, and Reaction records are declared at top-level scope with
static lifetime (§4.6). Their fields are fixed at declaration time and cannot
be updated after construction — a design choice that matches the reliability
goal of §4.1: a compound's formula or an element's atomic mass is a physical
constant, not a variable. Attempting to write to a record field is a semantic
error even though the grammar accepts the syntax.

Formula values derived from a compound declaration carry the same restriction.
`formula[element]` is a read-only atom count; reassigning it would silently
alter a compound's definition, which the static lifetime design prohibits.

Examples with valid assignment-target syntax:

```ans
mass = 18.0;
list[0] = water;
```

Function calls are not valid assignment targets because a function call
returns a value, not a storage location:

```ans
molar_mass(water) = 18.0; // invalid
```

## Augmented Assignment

ANS supports augmented assignment operators:

```ans
mass += element.atomic_mass * formula[element];
```

This is shorthand for:

```ans
mass = mass + (element.atomic_mass * formula[element]);
```

The operator must be valid for the variable's type. For example, `+=` is valid
for a numeric `mass` variable when the right-hand side is also numeric. The left
side must still match the same assignment-target grammar and must denote a
writable location. Augmented assignment is still a statement, so it also does not
produce a value.

This design gives ANS the common writable form needed for calculations like
molar mass while keeping assignment rules simple and reliable.
