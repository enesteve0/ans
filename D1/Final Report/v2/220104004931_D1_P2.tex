\section{4.1\quad Language Overview}

\textbf{Name.} \textbf{ANS}, short for \textit{Alchemist's Notation Script}.

\textbf{Intended domain.} ANS is a small DSL for chemistry programs. Its core objects are
elements, compounds, reactions, and stoichiometric calculations. I designed it so that chemistry
notation stays visible in the program: a user writes \code{H2O}, \code{CH4 + 2*O2}, and
\code{molar\_mass(water)} instead of hiding those ideas inside strings or generic arrays.

\subsection{Sample Program}
\begin{lstlisting}[style=ans]
// Elements and compounds
element H { atomic_mass = 1.008, valence = 1, symbol = "H" };
element O { atomic_mass = 15.999, valence = 2, symbol = "O" };
element C { atomic_mass = 12.011, valence = 4, symbol = "C" };

compound water   { formula = H2O, name = "Water" };
compound methane { formula = CH4, name = "Methane" };
compound co2     { formula = CO2, name = "Carbon dioxide" };
compound oxygen  { formula = O2, name = "Oxygen" };

function molar_mass(compound c) {
    let formula = c.formula;
    let mass = 0.0;
    for (let element in formula) {
        mass += element.atomic_mass * formula[element];
    }
    return mass;
};

reaction combustion {
    reactants = CH4 + 2*O2,
    products  = CO2 + 2*H2O,
    check     = balanced,
    energy    = exothermic 890.3 kJ/mol
};

let mass = molar_mass(water);
if (mass > 18.0) {
    print "Molar mass is above 18.";
} else {
    print "Molar mass is 18 or below.";
}
\end{lstlisting}

\subsection{Sebesta Evaluation Criteria}

Using Sebesta's criteria, ANS mainly chooses \textbf{readability}, \textbf{writability}, and
\textbf{reliability}. Readability matters because the course exam will ask us to defend the design,
and because chemistry code should look close to the equation it represents. Writability matters
because common tasks are short: declaring \code{compound water}, writing \code{2*O2}, and calling
\code{molar\_mass(water)} are all direct operations. Reliability matters most. Formula tokens,
typed parameters, units, and \code{check = balanced} give the compiler places to reject mistakes
before the program runs. I accept the cost: ANS is not general purpose, and the implementation
has to know about formulas, units, and reaction fields. For this project that trade-off is worth it.

The main point I would defend in the exam is that ANS is intentionally narrow. A general
language could calculate the same numbers, but the source code would not show the chemistry
as clearly. In ANS, the syntax itself records which names are elements, which names are
compounds, and which expression is a reaction side.

\section{4.2\quad Lexical Structure}

The scanner is mostly conventional: it recognizes identifiers, literals, keywords, operators,
separators, comments, and whitespace. The chemistry-specific rule is that uppercase tokens are
formula literals, while lowercase names are identifiers or keywords. This keeps \code{H2O} and
\code{water} visually and lexically separate.

{\footnotesize
\begin{tabularx}{\linewidth}{@{}p{2.65cm}p{3.7cm}Y@{}}
\toprule
\textbf{Category} & \textbf{Examples} & \textbf{Pattern or rule} \\
\midrule
Identifiers & \code{water}, \code{mass}, \code{compute\_yield} & \rx{[a-z\_][A-Za-z0-9\_]*} \\
Number literal & \code{20}, \code{1.008}, \code{6.02e23} & \rx{(?:0|[1-9][0-9]*)(?:\textbackslash.[0-9]+)?(?:[eE][+-]?[0-9]+)?} \\
String literal & \code{"Water"} & double quoted text with escapes \\
Char literal & \code{'H'}, \code{'\textbackslash{}n'} & one character or escape in single quotes \\
Formula literal & \code{H}, \code{O2}, \code{H2O}, \code{CH4} & \rx{(?:[A-Z][a-z]?(?:[1-9][0-9]*)?)+} \\
Unit literal & \code{g/mol}, \code{kg/mol}, \code{kJ/mol} & longest match before the slash operator \\
Hard keywords & \code{let}, \code{function}, \code{return}, \code{for}, \code{in}, \code{if}, \code{elif}, \code{else}, \code{print} & identifier text, then keyword table lookup \\
Context words & \code{element}, \code{compound}, \code{reaction}, \code{balanced} & parsed by grammar position \\
Operators & \code{==}, \code{!=}, \code{+=}, \code{=}, \code{+}, \code{-}, \code{*}, \code{/}, \code{<}, \code{>} & longer operators before shorter ones \\
Separators & \code{\{} \code{\}} \code{(} \code{)} \code{[} \code{]} \code{,} \code{;} \code{.} & single character tokens \\
Comments & \code{// comment} & skipped until newline \\
\bottomrule
\end{tabularx}}

Single word units such as \code{mol}, \code{g}, \code{kg}, and \code{kJ} are scanned as identifiers.
The parser treats them as units only after a number. So \code{5.0 mol} is a quantity, but \code{mol}
can still be a normal parameter name in another context. This is simpler than making the lexer
stateful.

This also makes error handling easier to explain. If the scanner sees an uppercase token, it goes
through the formula path. If the parser sees \code{890.3 kJ/mol}, it accepts a quantity because the
unit follows a number. If the same unit appears where an expression cannot contain a quantity,
the parser can report the mistake without relying on hidden lexer state.

\section{4.3\quad Syntax (EBNF)}

This is the Part 1 grammar. It is written for a recursive-descent parser, so precedence and
ambiguous-looking cases are separated into different non-terminals.

\begin{lstlisting}[style=ebnf]
<program> -> { <top_level_statement> } EOF
<top_level_statement> -> <element_declaration> ";"
                       | <compound_declaration> ";"
                       | <reaction_declaration> ";"
                       | <function_declaration> ";"
                       | <variable_declaration> ";"
                       | <assignment_statement> ";"
                       | <augmented_assignment_statement> ";"
                       | <print_statement> ";"
                       | <expression_statement> ";"
                       | <if_statement>

<block> -> "{" { <statement> } "}"
<statement> -> <variable_declaration> ";"
             | <assignment_statement> ";"
             | <augmented_assignment_statement> ";"
             | <return_statement> ";"
             | <print_statement> ";"
             | <expression_statement> ";"
             | <for_statement>
             | <if_statement>

<variable_declaration> -> "let" <identifier> "=" <expression>
<assignment_statement> -> <assignable> "=" <expression>
<augmented_assignment_statement> -> <assignable> <augmented_assignment_operator> <expression>
<augmented_assignment_operator> -> "+=" | "-=" | "*=" | "/="
<return_statement> -> "return" [ <expression> ]
<print_statement> -> "print" <expression>
<expression_statement> -> <expression>

<function_declaration> -> "function" <identifier> "(" [ <parameter_list> ] ")" <block>
<parameter_list> -> <parameter> { "," <parameter> }
<parameter> -> [ <type_name> ] <identifier>
<type_name> -> "element" | "compound" | "reaction"

<for_statement> -> "for" "(" "let" <identifier> "in" <expression> ")" <block>
<if_statement> -> "if" "(" <expression> ")" <block> { <elif_clause> } [ <else_clause> ]
<elif_clause> -> "elif" "(" <expression> ")" <block>
<else_clause> -> "else" <block>

<element_declaration> -> "element" <element_symbol> "{" <element_field_list> "}"
<element_symbol> -> <formula_literal>
<element_field_list> -> <element_field> { "," <element_field> } [ "," ]
<element_field> -> "atomic_mass" "=" <number_literal>
                 | "valence" "=" <number_literal>
                 | "symbol" "=" <string_literal>

<compound_declaration> -> "compound" <identifier> "{" <compound_field_list> "}"
<compound_field_list> -> <compound_field> { "," <compound_field> } [ "," ]
<compound_field> -> "formula" "=" <formula_literal>
                  | "name" "=" <string_literal>

<reaction_declaration> -> "reaction" <identifier> "{" <reaction_field_list> "}"
<reaction_field_list> -> <reaction_field> { "," <reaction_field> } [ "," ]
<reaction_field> -> "reactants" "=" <reaction_expression>
                  | "products" "=" <reaction_expression>
                  | "check" "=" <balance_check>
                  | "energy"    "=" <energy_expression>
<balance_check> -> "balanced"
<energy_expression> -> <energy_kind> <quantity_literal>
<energy_kind> -> "exothermic" | "endothermic"

<reaction_expression> -> <reaction_term> { "+" <reaction_term> }
<reaction_term> -> <species_ref> | <coefficient> "*" <species_ref>
<coefficient> -> <number_literal>
<species_ref> -> <formula_literal> | <identifier>

<expression> -> <comparison_expression>
<comparison_expression> -> <additive_expression>
                           [ ( "==" | "!=" | ">=" | "<=" | ">" | "<" ) <additive_expression> ]
<additive_expression> -> <multiplicative_expression>
                         { ( "+" | "-" ) <multiplicative_expression> }
<multiplicative_expression> -> <unary_expression>
                               { ( "*" | "/" ) <unary_expression> }
<unary_expression> -> [ "-" ] <postfix_expression>
<postfix_expression> -> <primary_expression> { <postfix_operator> }
<postfix_operator> -> "." <identifier> | "[" <expression> "]" | "(" [ <argument_list> ] ")"
<primary_expression> -> <number_or_quantity_literal>
                      | <string_literal>
                      | <char_literal>
                      | <list_literal>
                      | <formula_literal>
                      | <identifier>
                      | "(" <expression> ")"

<argument_list> -> <expression> { "," <expression> }
<number_or_quantity_literal> -> <number_literal> [ <unit> ]
<quantity_literal> -> <number_literal> <unit>
<unit> -> UNIT_LITERAL | "mol" | "g" | "kg" | "kJ"
<list_literal> -> "[" [ <argument_list> ] "]"

<assignable> -> <identifier> { <assignable_postfix> }
<assignable_postfix> -> "." <identifier> | "[" <expression> "]"

<identifier> -> IDENTIFIER
<number_literal> -> NUMBER_LITERAL
<string_literal> -> STRING_LITERAL
<char_literal> -> CHAR_LITERAL
<formula_literal> -> FORMULA_LITERAL
\end{lstlisting}

\subsection{Ambiguity Notes}
\begin{itemize}
  \item Arithmetic precedence is encoded by grammar levels, not by a later fix-up step.
  \item Reaction expressions use their own grammar. In \code{CH4 + 2*O2}, the \code{*} belongs to the coefficient \code{2}.
  \item ANS requires \code{2*O2}, not \code{2O2}, so coefficients and formula subscripts are not mixed.
  \item Formula literals start uppercase and identifiers start lowercase or underscore.
  \item \code{element}, \code{compound}, and \code{reaction} become type names only inside parameter lists.
  \item Braced blocks remove the usual dangling \code{else} problem.
\end{itemize}

The grammar also separates assignment targets from general expressions. Function calls are
valid expressions, but they are not valid assignment targets. That keeps a line such as
\code{f(x) = 3} invalid instead of forcing the language to define assignment to a function result.

\section{4.6\quad Names, Binding, Scope, and Lifetime}

\textbf{Identifiers.} A legal identifier matches \code{[a-z\_][A-Za-z0-9\_]*}. ANS is
case-sensitive. This is also how the language separates names from chemistry notation:
\code{water} is an identifier, but \code{H2O} and \code{CO2} are formula literals. The hard
reserved words are \code{let}, \code{function}, \code{return}, \code{for}, \code{in}, \code{if},
\code{elif}, \code{else}, and \code{print}. Chemistry words such as \code{compound} and
\code{reaction} are contextual.

\textbf{Binding times.} Most reliability-related bindings happen before execution. The lexer
binds lexemes to token categories. The parser binds names to declaration forms and parameters
to optional type annotations. The later semantic phase binds compounds and reactions to their
declarations, validates formulas, and checks \code{check = balanced}. Runtime binding is still used
for argument values, local storage, loop iteration values, and ordinary variable values.

{\footnotesize
\begin{tabularx}{\linewidth}{@{}p{4.1cm}p{3.2cm}Y@{}}
\toprule
\textbf{Binding} & \textbf{When} & \textbf{Example} \\
\midrule
Lexeme to token category & Lex time & \code{water} is an identifier, \code{H2O} is a formula. \\
Identifier to declaration & Compile time & \code{mass} resolves by static scope. \\
Parameter to declared type & Compile time & \code{compound c} marks \code{c} as a compound parameter. \\
Reaction balance decision & Compile time & \code{check = balanced} asks for atom-count validation. \\
Parameter to argument value & Run time & \code{molar\_mass(water)} binds \code{c} to \code{water}. \\
Local variable to storage & Run time & \code{let mass = 0.0} allocates during the call. \\
\bottomrule
\end{tabularx}}

\textbf{Scope.} ANS uses static scoping. A name is resolved by looking in the current block and
then outward in the source text. I chose this because chemistry calculations should not depend
on who called a function. If lookup were dynamic, a local name in the caller could silently change
what \code{molar\_mass} or \code{compute\_yield} means.

For example, if a caller had a local variable named \code{water}, dynamic scoping could make a
function read that caller's binding instead of the compound declaration the function was written
against. That would be confusing in any language, but in a chemistry DSL it is especially bad
because the same expression could refer to a different compound depending on the call chain.

{\footnotesize
\begin{tabularx}{\linewidth}{@{}p{4.2cm}p{3.1cm}Y@{}}
\toprule
\textbf{Entity} & \textbf{Lifetime} & \textbf{Reason} \\
\midrule
Top-level elements, compounds, reactions & Static & They describe the program's chemistry model. \\
Top-level \code{let} variables & Static & They live for the whole run. \\
Function parameters & Stack-dynamic & Each call gets its own arguments. \\
Local \code{let} variables & Stack-dynamic & They disappear when the block exits. \\
\code{for} loop variable & Stack-dynamic & It belongs only to the loop body. \\
Lists and chemistry objects & Implicit heap-dynamic & The runtime manages them. ANS has no \code{new}, \code{delete}, or pointers. \\
\bottomrule
\end{tabularx}}

This lifetime design follows the reliability goal. The programmer works with formulas and
reactions, not manual memory management.

\section{4.4\quad Operational Semantics}

Following Sebesta \S3.5, I describe the meaning of the non-trivial constructs by showing what they do to an abstract machine state. That state contains the current environment, the runtime store, and the global chemistry table of declared elements, compounds, reactions, and functions. The two main constructs are the \code{for}-in loop and the \code{check = balanced} reaction declaration.

\textbf{Helper operations:}
\begin{lstlisting}[style=sem]
current_scope          the active lexical environment frame
evaluate(E)            evaluate expression E and return its value
execute(S)             execute statement or block S
new_scope(parent)      create a nested lexical scope frame with given parent
lookup(name)           find a name by static-scope chain walk
semantic_error(M)      stop with compile-time error message M
runtime_error(M)       stop at run time with message M

parse_formula(F)       convert formula literal to {symbol -> count} map + order list
formula_elements(F)    return element symbols in first-appearance (left-to-right) order
formula_count(F, E)    return count of element E in formula F (0 if absent)
species_formula(S)     formula value of a reaction species (see below)
reaction_atoms(R)      atom-count map for a reaction expression (see below)
atom_maps_equal(A, B)  true iff every symbol has equal count in A and B
\end{lstlisting}

\subsection{4.4.1\quad For-in Loop}

\textbf{Formula iteration.}\; When the iterable evaluates to a Formula, the loop visits each distinct element in first-appearance order.

\begin{lstlisting}[style=sem]
F = evaluate(collection)

if type(F) is formula:
    for each symbol S in formula_elements(F), left to right:
        if S is not a declared element:
            semantic_error("formula uses undeclared element")
        iter_scope = new_scope(current_scope)
        bind variable in iter_scope to the Element object for S
        execute body using iter_scope
        destroy iter_scope
    end
\end{lstlisting}

For \code{H2O} the body runs first for \code{H}, then for \code{O}. If the formula is empty, the body executes zero times. After the iteration scope is destroyed, the loop variable is inaccessible.

\textbf{ReactionSide iteration.}\; When the iterable is a ReactionSide, the loop visits each species in declaration order.

\begin{lstlisting}[style=sem]
R = evaluate(collection)

if type(R) is reaction_side:
    for each term T in R, left to right:
        iter_scope = new_scope(current_scope)
        if T.species does not resolve to a declared Compound:
            semantic_error("reaction species must name a compound")
        bind variable in iter_scope to the resolved Compound value
        execute body using iter_scope
        destroy iter_scope
    end
\end{lstlisting}

Iterating over the reactants of \code{CH4 + 2*O2} (with \code{methane} and \code{oxygen} declared) yields \code{methane} first, then \code{oxygen}, because formula-literal species must resolve to declared compounds before execution. Unresolved formulas are semantic errors. Coefficients are accessible via \code{reaction\_side[compound]}.

\textbf{Scoping.}\; Both forms create a fresh nested scope per iteration. Inner declarations vanish at scope destruction. Assignment to an outer variable updates it through the static-scope chain.

\textbf{Formula indexing} --- \code{formula[element]}:

\begin{lstlisting}[style=sem]
F = evaluate(formula);  E = evaluate(element)
if type(F) != formula:  semantic_error("left of [] must be formula")
if type(E) != element:  semantic_error("formula index must be element")
result = formula_count(F, E)    // 0 if element absent
\end{lstlisting}

This lets the molar-mass calculation \code{mass += element.atomic\_mass * formula[element]} be executed as: \texttt{count = formula\_count(F, E);\ term = element.atomic\_mass * count;\ mass = mass + term}.

\subsection{4.4.2\quad Reaction Balance Check: \code{check = balanced}}

\begin{lstlisting}[style=sem]
if N already in chemistry table:
    semantic_error("reaction already declared")
if any required field (reactants/products/check/energy) is missing:
    semantic_error("reaction missing required field")
if any field appears more than once:
    semantic_error("reaction has duplicate field")
if check != balanced:
    semantic_error("check must be 'balanced'")
if D not in {exothermic, endothermic}:
    semantic_error("energy direction must be exothermic or endothermic")
if energy unit not in {kJ, kJ/mol}:
    semantic_error("energy unit must be kJ or kJ/mol")

left_atoms  = reaction_atoms(R)
right_atoms = reaction_atoms(P)
if NOT atom_maps_equal(left_atoms, right_atoms):
    semantic_error("reaction is not balanced")

bind N -> Reaction(N, R, P, D, energy_value, balanced=true)
\end{lstlisting}

\textbf{Species formula} (\code{species\_formula(S)}): if \code{S} is a formula literal, parse it and require it to match a declared compound; if \code{S} is an identifier, require it to name a declared compound and return that compound's formula; otherwise \code{semantic\_error}.

\textbf{Atom maps}: \code{reaction\_atoms} accumulates $\mathrm{coeff}_i \times \mathrm{parse\_formula(species}_i)$ across all terms. Scalar multiplication multiplies every count; addition merges keys (missing $= 0$). For combustion:

\begin{lstlisting}[style=sem]
reaction_atoms(CH4 + 2*O2) = {C:1,H:4} + 2*{O:2} = {C:1, H:4, O:4}
reaction_atoms(CO2 + 2*H2O) = {C:1,O:2} + 2*{H:2,O:1} = {C:1, H:4, O:4}
\end{lstlisting}

Both sides equal, so the reaction passes.

\section{4.5\quad Type System}
\textit{Citing Sebesta Ch.\,6.}

ANS is statically typed. Its type system has four primitive types, one parameterised collection (\code{List<T>}), and a fixed set of chemistry domain types.

\subsection{Primitive Types (Sebesta \S6.2)}

\begin{tabularx}{\textwidth}{@{} L{2.1cm} L{2.2cm} Y @{}}
\toprule
\textbf{Type} & \textbf{Surface syntax} & \textbf{Value set} \\
\midrule
Number   & \code{20}, \code{1.008} & IEEE-754 double. No separate integer type; \code{20} and \code{20.0} are equal. \\
String   & \code{"Water"}          & Unicode sequence with escapes \texttt{\textbackslash" \textbackslash\textbackslash\ \textbackslash n \textbackslash r \textbackslash t}. \\
Character& \code{'H'}, \code{'\textbackslash{}n'} & Single Unicode character, same escapes. \\
Boolean  & \textit{no literal}     & Produced by comparison operators; consumed by \code{if}/\code{elif}. No \code{true}/\code{false} keywords. \\
\bottomrule
\end{tabularx}

\subsection{Domain Types}

\begin{itemize}
\item \textbf{Quantity} --- a (Number, unit) pair. Units: \code{mol}, \code{g}, \code{kg}, \code{kJ}, \code{g/mol}, \code{kg/mol}, \code{kJ/mol}. Surface: \code{5.0 mol}, \code{890.3 kJ/mol}.
\item \textbf{Formula} --- an ordered map from element symbol to atom count plus first-appearance iteration order (\S4.4). Surface: \code{H2O}, \code{CH4}.
\item \textbf{List\texttt{<T>}} --- homogeneous sequence of any type \code{T}, 0-indexed, runtime bounds-checked.
\item \textbf{Element} / \textbf{Compound} / \textbf{Reaction} --- record-like aggregates with fixed, language-defined schemas.
\item \textbf{ReactionSide} --- the type of \code{.reactants} and \code{.products} fields; a list of (coefficient, species) terms. Not a declarable type annotation.
\end{itemize}

\subsection{Strong Typing (Sebesta \S6.14)}

ANS is \textbf{strongly typed}: every type error is detected at compile time. Typed parameters and built-in calls such as \code{mol(...)} are checked at call sites; every formula symbol must resolve to a declared element; reaction-side formulas must resolve to declared compounds; every \code{check = balanced} reaction must conserve atoms; each \code{let} binding fixes its variable's type from the right-hand side; every list literal is checked for homogeneity. There are no silent dimension or kind conversions --- a Quantity is not addable to a Number, a Compound is not implicitly a Formula.

\subsection{Implicit Type Coercion (Sebesta \S7.4)}

ANS performs \textbf{no implicit coercions}. Integer-shaped literals (\code{20} vs.\ \code{20.0}) are the same Number value; there is no second numeric type to convert from. Stoichiometric coefficients (\code{2} in \code{2*O2}) are plain Numbers used in atom-map arithmetic. Explicitly rejected: Number $\leftrightarrow$ String, Character $\leftrightarrow$ String, Element $\leftrightarrow$ Formula, Quantity $\leftrightarrow$ Quantity across different units (\code{5 g} $\not\to$ \code{5 kg}). Each rejection eliminates a class of chemistry-calculation bug.

\subsection{Type Equivalence (Sebesta \S6.15)}

ANS uses three rules:
\begin{enumerate}[leftmargin=1.5em,itemsep=2pt]
\item \textbf{Name equivalence for primitives and domain types.} Element, Compound, Reaction, Number, String, Character, Boolean, Formula are equivalent only when their declared type-kind names match. Two compounds with identical formulas are still different values with type \code{compound} --- the type system tracks \emph{kind}, not identity.
\item \textbf{Unit-tag compatibility for Quantities.} Two Quantities share a type when their unit tags match exactly (\code{5 mol} and \code{7 mol} compatible; \code{5 mol} and \code{7 g/mol} not).
\item \textbf{Structural equivalence for \code{List<T>}.} \code{List<T1>} and \code{List<T2>} are the same type if and only if \code{T1} $\equiv$ \code{T2} by the rules above.
\end{enumerate}

Only one comparison per expression; \code{a < b < c} is not a chained comparison and must be rewritten as separate conditions.

\subsection{Boolean Expressions and Short-Circuiting}
ANS has no Boolean operators (\code{\&\&}, \code{||}, \code{and}, \code{or}), so short-circuit evaluation does not apply. An \code{if}/\code{elif} condition must evaluate to a Boolean value produced by a comparison expression; plain numbers or strings are not accepted as conditions. Compound conditions must be nested as separate \code{if} statements.

\subsection{Operand Evaluation Order}
ANS defines \textbf{left-to-right} evaluation (Sebesta \S7.2). For \code{a + b}, \code{a} is evaluated before \code{b}. For \code{f(a, b, c)}, arguments are evaluated left to right before function entry. For \code{formula[element]}, \code{formula} is evaluated before \code{element}.

\subsection{Type Rules}
No implicit coercion (\S4.5). Arithmetic operators require Number operands:
\begin{center}
\code{Number} $\{+, -, *, /\}$ \code{Number} $\to$ \code{Number} \qquad
\code{Formula[Element]} $\to$ \code{Number}
\end{center}
Quantity values appear as stored literals (e.g.\ reaction energy fields); arithmetic on Quantities is not defined in this subset. Different-unit Quantities are not interchangeable even with the same operator.

\subsection{Assignment}
Assignment is a \textbf{statement}, not an expression. \code{mass = 18.0;} updates \code{mass} but produces no value; expression-style assignment (\code{if (x = 3)}) is invalid. Valid assignment targets: \code{let} variables and list elements. Read-only targets (record fields, formula atom counts, function call results) are rejected by the semantic checker. Augmented assignment (\code{mass += term}) requires both sides to be Number and the left side to be a writable location.

\section{4.8\quad Design Rationale}

These are the five decisions from sections 4.5--4.7 that I think matter most, explained using Sebesta Ch.\,5--7 terminology.

\textbf{1. Static strong typing with no implicit coercion} (Sebesta \S6.14, \S7.4). Chemistry calculations depend on matching the right kinds of values: a Number, Formula, Compound, and Quantity are not interchangeable. \code{5 g + 2 mol} is rejected instead of guessed. This supports Sebesta's \emph{reliability} criterion because mistakes show up before execution. The trade-off is lower convenience: programmers must match types and units explicitly instead of relying on automatic conversion.

\textbf{2. Quantities with units as a domain type} (Sebesta \S6.2). A value such as \code{890.3 kJ/mol} is not just a plain number; it is an energy quantity with a specific unit. Keeping the unit inside the type makes reaction code easier to read and lets the type checker reject unit mistakes at compile time. The trade-off is higher implementation cost --- the lexer, parser, checker, and interpreter all have to preserve unit information --- and slightly more writing effort, because units must be written explicitly.

\textbf{3. Static lexical scoping} (Sebesta \S5.5). Chemistry functions should not change meaning depending on who calls them. \code{molar\_mass(water)} must resolve \code{water}, \code{formula}, and \code{element} from the source structure, not from a caller's local variables. This makes compound references and formula calculations easier to follow. The trade-off is implementation complexity: the interpreter must maintain nested environment frames and the checker must walk the scope chain to validate names.

\textbf{4. Left-to-right operand evaluation} (Sebesta \S7.2). I chose left-to-right evaluation so expression behaviour stays predictable. Every implementation should run operands in the same order, which matters when function calls have side effects. The trade-off is that the interpreter cannot freely reorder operands for optimisation.

\textbf{5. Assignment as a statement, not an expression} (Sebesta \S7.7). \code{mass = 18.0;} updates a storage location but does not produce a value, so it cannot appear inside another expression. This avoids confusing code such as \code{if (mass = 18.0)} and keeps assignment \code{=} separate from equality \code{==}. The trade-off is less compact syntax: chained assignments such as \code{x = y = 0} are not allowed.
