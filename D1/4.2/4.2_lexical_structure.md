# 4.2 Lexical Structure

ANS uses six token categories — identifiers, literals, keywords, operators, separators, and comments — produced by a finite-automaton-based scanner followed by a reserved-word filter, in the style described by Sebesta (§4.2). Two design decisions drive the layout: (i) chemical formula tokens (`H2O`, `CH4`) must be distinguishable from user-defined names, solved by case (identifiers begin lowercase; formula tokens begin uppercase); and (ii) several chemistry words (`reaction`, `compound`, `mol`) must still be usable as ordinary parameter names, solved by treating them as *contextual* keywords that the **parser** — not the lexer — promotes to keyword status depending on grammar position.

---

## Token Categories

### 1. Identifiers

User-defined names for variables, functions, compounds, and reactions.

```
[a-z_][A-Za-z0-9_]*
```

Examples: `water`, `mass`, `compute_yield`, `reactant_mol`

---

### 2. Literals

ANS has five literal sub-categories.

#### Number literal
```
(?:0|[1-9][0-9]*)(?:\.[0-9]+)?(?:[eE][+-]?[0-9]+)?
```
Examples: `20`, `1.008`, `21.2`, `890.3`, `6.02e23`

#### String literal
```
"(?:[^"\\\r\n]|\\["\\nrt])*"
```
Examples: `"Hydrogen"`, `"Water"`, `"Carbon dioxide"`

#### Character literal
```
'(?:[^'\\\r\n]|\\['\\nrt])'
```
Examples: `'H'`, `'\n'`

#### Formula literal
```
(?:[A-Z][a-z]?(?:[1-9][0-9]*)?)+
```
Examples: `H`, `O`, `H2O`, `CH4`, `CO2`, `O2`

> **Note — subscript 1:** The pattern accepts a subscript of 1, so `H1` is a lexically valid formula literal. In standard chemistry `H` and `H1` denote the same species; the semantic checker normalises `H1` to `H`. A token sequence like `H1O` is lexed as two consecutive formula literals (`H1` and `O`), which the semantic phase rejects as a malformed compound formula.

#### Unit literal (compound forms only)
```
kg/mol | g/mol | kJ/mol
```
Examples: `g/mol`, `kg/mol`, `kJ/mol`

These three tokens contain `/` and therefore can never be valid identifiers. The lexer recognises them by simple pattern priority over the `/` operator — a straightforward longest-match rule, with no lookahead or lexer statefulness required.

Single-word unit words — `mol`, `g`, `kg`, `kJ` — all match the identifier pattern and are **always emitted as `IDENTIFIER` tokens** by the scanner. The parser promotes them to a `<unit>` role only when they directly follow a number literal inside a `<number_or_quantity_literal>` or `<quantity_literal>` rule. Everywhere else (function parameters, property names, arithmetic expressions) they remain plain identifiers. This removes any need for a stateful or context-sensitive lexer: the `5.0 mol` sequence is tokenised as `NUMBER_LITERAL IDENTIFIER`, and the grammar rule

```
<number_or_quantity_literal> → <number_literal> [ <unit> ]
<unit>                       → UNIT_LITERAL | "mol" | "g" | "kg" | "kJ"
```

handles the pairing entirely at the parser level.

> **Notation note:** the quoted alternatives `"mol"`, `"g"`, `"kg"`, `"kJ"` in the `<unit>` rule match an `IDENTIFIER` token whose lexeme equals that string — they are not a separate token class. The lexer emits `IDENTIFIER` in all four cases; the parser accepts the token by lexeme value, exactly as it does for other contextual keywords such as `"balanced"` and `"exothermic"`.

---

### 3. Keywords

The scanner always produces an `IDENTIFIER` token for every word-shaped lexeme. A **reserved-word filter** (outside the FA proper) then promotes tokens to `KEYWORD` if their lexeme is in the hard reserved-word table — the standard technique described by Sebesta (§5.1). Contextual keywords are promoted further by the **parser** based on grammar position.

#### Hard reserved words — may never be used as identifiers

```
let  function  return  for  in  if  elif  else  print
```

#### Contextual keywords — promoted by the parser, not the lexer

| Grammar position | Words |
|---|---|
| Declaration head | `element`  `compound`  `reaction` |
| Declaration field names | `atomic_mass`  `valence`  `symbol`  `formula`  `name`  `reactants`  `products`  `check`  `energy` |
| Reaction field values | `balanced`  `exothermic`  `endothermic` |
| Parameter type annotations | `element`  `compound`  `reaction` |

> **Disambiguation for `element`, `compound`, `reaction`:** these three words appear in both the *declaration head* and the *parameter type annotation* positions. Because promotion is done by the parser, the parser resolves which role applies from surrounding grammar context: immediately following `function … (` and preceding a bare identifier → type annotation; at the start of a top-level statement → declaration keyword. The scanner emits the same `IDENTIFIER` token in both cases.

---

### 4. Operators

```
==  !=  <=  >=  +=  -=  *=  /=  =  +  -  *  /  <  >
```

Pattern: `==|!=|<=|>=|\+=|-=|\*=|/=|=|[+\-*/><]`

Longer patterns are tried first: `+=` before `+`, `==` before `=`, `<=` before `<`, `>=` before `>`. The `/` character is matched as an operator only when it is not part of a `UNIT_LITERAL` (`g/mol`, `kg/mol`, `kJ/mol`); since those patterns are tried first by lexer priority, a bare `/` in arithmetic is never misidentified as part of a unit.

---

### 5. Separators

```
{  }  (  )  [  ]  ,  ;  .
```

Pattern: `[{}()\[\],;.]`

---

### 6. Comments and Whitespace

| Category | Pattern | Notes |
|---|---|---|
| Line comment | `//[^\r\n]*` | Discarded; not passed to the parser |
| Whitespace | `[ \t\f\r\n]+` | Token separator only; not a token |

---

> **Boolean literals (`true` / `false`):** ANS does not define `true` or `false` as token categories. Comparison expressions (`x > 0`, `a == b`) produce boolean *values* at runtime, but those values have no literal surface syntax in Part 1. Whether boolean values can be stored in a `let` variable and what token a subsequent `print` would produce are addressed in §4.5 (Type System).
