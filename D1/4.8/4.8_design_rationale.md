# 4.8 Design Rationale

This section explains five selected ANS design decisions from the type system,
scoping, expressions, and assignment rules, using Sebesta Ch. 5-7 terminology.
Each choice favors chemistry-program reliability, while accepting a clear
trade-off.

ANS uses **static strong typing with no implicit coercion** because chemistry
calculations depend on using the right kind of value in the right place. A
Number, Formula, Compound, Element, and Quantity are not interchangeable. For
example, `5 g + 2 mol` should be rejected instead of accepted or guessed by the
language. This supports Sebesta's reliability criterion because mistakes are
caught before execution. The trade-off is lower convenience: programmers must
write values with matching types and units instead of relying on automatic
conversion.

ANS treats **quantities with units as a domain type** because units are part of
the meaning of chemistry data. A value like `890.3 kJ/mol` is not just a plain
number; it represents an energy quantity with a specific unit. Keeping the unit
inside the type makes reaction code more readable and helps the type checker
reject unit mistakes. The trade-off is twofold: higher implementation cost, because the lexer,
parser, semantic checker, and interpreter must all preserve and check unit
information; and higher writability cost to the programmer, who must always
write units explicitly — `890.3 kJ/mol` instead of just `890.3` — even for
quick intermediate calculations.

ANS uses **static lexical scoping** (Sebesta §5.5) because chemistry functions
should not change meaning depending on who calls them. A function such as
`molar_mass(water)` should resolve `water`, `formula`, and `element` according
to the source structure, not according to a caller's local variables at run time.
This makes compound references and formula calculations easier to reason about.
The trade-off is implementation complexity: the compiler needs nested symbol
tables instead of one simple global-name lookup.

ANS defines **left-to-right operand evaluation** (Sebesta §7.2) so expression
behavior is predictable. In an expression such as `mass + element.atomic_mass *
formula[element]`, precedence decides the operator grouping, and left-to-right
evaluation decides the order in which the operands are processed.
This matters for function calls, indexing, and future error cases because every
implementation should report the same behavior. The trade-off is less freedom
for optimization, since the interpreter cannot freely reorder operand evaluation.

ANS keeps **assignment as a statement, not an expression** (Sebesta §7.7). A statement such as
`mass = 18.0;` updates a storage location, but it does not produce a value that
can be used inside another expression. This rejects confusing code such as
`if (mass = 18.0)` and keeps assignment `=` separate from equality comparison
`==`, which is especially helpful for beginners reading ANS programs. The
trade-off is reduced compactness: chained assignments like `x = y = 0` are not
allowed, so the programmer must write separate assignment statements.
