# 4.6 Names, Binding, Scope, and Lifetime

*Citing Sebesta Ch. 5*

---

## Legal Identifiers (Sebesta §5.1)

An ANS identifier must match the pattern `[a-z_][A-Za-z0-9_]*`: it begins with a lowercase letter or underscore and continues with any mix of letters, digits, and underscores. ANS is **case-sensitive**, so `water` and `Water` are entirely different tokens — and in fact `Water` is not a legal identifier at all, because any token beginning with an uppercase letter is classified as a `FORMULA_LITERAL` by the lexer (`H`, `O2`, `H2O`). This case split is a deliberate design choice: chemistry notation and program names are kept visually separate with no additional keyword rules.

**Hard reserved words** — may never be used as identifiers:

```
let  function  return  for  in  if  elif  else  print
```

**Contextual keywords** — reserved only in specific grammar positions; valid identifiers everywhere else:

```
element  compound  reaction
atomic_mass  valence  symbol  formula  name
reactants  products  check  balanced  energy  exothermic  endothermic
```

This means `function compute_yield(reaction r, compound c)` is legal: `reaction` and `compound` act as type annotations inside the parameter list, but the same words are plain identifiers in expressions. A name may not be declared twice in the same scope. An inner-scope `let` may shadow an outer binding — for example, `let formula = c.formula` inside `molar_mass` shadows the contextual field keyword `formula` — a warning for this will be emitted by the semantic checker in Part 2.

## Bindings: Compile Time vs. Run Time (Sebesta §5.2)

| Binding | When | Example from `main.ans` |
|---|---|---|
| Operator symbol → semantics | Language-design time | `+`, `*`, `==`, `+=` |
| Lexeme → token category | Lex / compile time | `water` → `IDENTIFIER`, `H2O` → `FORMULA_LITERAL` |
| Identifier → declaration | Compile time (static scope walk) | `mass` in `molar_mass` resolves to its `let` declaration |
| Variable → inferred type | Compile time | `let n = 21.2` → Float; `let name = "Hydrogen"` → String |
| Parameter → declared type | Compile time | `compound c` in `molar_mass` fixes `c` as Compound |
| Element / compound / reaction → declaration | Compile time | `water`, `combustion` resolved before execution |
| Formula validity | Compile time | every symbol in `H2O` must name a declared element |
| `check = balanced` | Compile time | atom counts on both sides verified statically |
| `mol` → built-in function declaration | Compile time | pre-declared; resolved before any user code is checked |
| Parameter → argument value | Run time (call) | `molar_mass(water)` binds `c` to the `water` object |
| Local variable → storage cell | Run time (block entry) | `let mass = 0.0` allocates on function entry |
| Variable → value | Run time (assignment) | `mass += element.atomic_mass * formula[element]` |
| Loop variable → current element | Run time (each iteration) | `let element in formula` rebinds each step |
| Function call → return value | Run time | `return mass` passes the computed float back |

ANS maximises **compile-time bindings** by design: type inference, formula validation, and balance checking all happen before execution, catching chemistry errors as early as possible.

## Static Scoping vs. Dynamic Scoping (Sebesta §5.5)

ANS uses **static (lexical) scoping**. Every name resolves to the nearest enclosing declaration in the *source text*: the current block, then each successively enclosing block, up to the top-level program scope.

### Why static scoping?

Because ANS performs compile-time formula validation and balance checking, the compiler must be able to determine which compound or reaction a name refers to from the source text alone — without simulating execution. Static scoping makes this possible. It also makes programs easier to read: the meaning of every name can be found by looking upward in the source without knowing the call history.

### What would break under dynamic scoping?

Consider this pair of functions from `main.ans`:

```ans
function molar_mass(compound c) {
    let formula = c.formula;
    let mass = 0.0;
    for (let element in formula) {
        mass += element.atomic_mass * formula[element];
    }
    return mass;
};

function compute_yield(reaction r, compound c) {
    let products = r.products;
    let reactants = r.reactants;
    let reactant_mol = 1.0 / mol(reactants[c]);
    let product_mol = reactant_mol * mol(products[c]);
    return product_mol;
};
```

Under **dynamic scoping**, `formula` inside `molar_mass` would not refer to the local `let formula = c.formula` but to whatever binding of `formula` happened to exist in the caller's scope at the moment of the call. If `compute_yield` called `molar_mass` and the caller had its own `let formula = ...`, the calculation would silently use the wrong data. More critically, `element` in the `for` loop would capture any `element` variable visible in the call chain, potentially iterating over a chemistry declaration object rather than a formula map. The compile-time balance check on `reaction combustion` depends on statically resolving `CH4`, `O2`, `CO2`, and `H2O` to their declared compounds; under dynamic scoping that resolution would be deferred to run time, making static verification impossible.

## Lifetime of Variables (Sebesta §5.4.3)

| Entity | Lifetime | Notes |
|---|---|---|
| `element H { ... }`, `element O { ... }`, `element C { ... }` | **Static** | Allocated once at program start; visible to every subsequent statement and function |
| `compound water { ... }`, `compound methane { ... }`, etc. | **Static** | Same as element declarations |
| `reaction combustion { ... }`, `reaction combustion2 { ... }` | **Static** | Verified at compile time; exists for the program's entire lifetime |
| Top-level `let num`, `let name`, `let elements`, `let compounds`, etc. | **Static** | Single binding from declaration to program termination |
| Function parameters (`reaction r`, `compound c`) | **Stack-dynamic** | Allocated on each call to `compute_yield` or `molar_mass`; deallocated on return. Supports recursion. |
| Local `let` inside a function (`let formula`, `let mass`, `let products`) | **Stack-dynamic** | Allocated when the declaration is reached during execution; freed when the enclosing block exits |
| `for` loop variable (`let element in formula`) | **Stack-dynamic** | Bound at the start of the `for` block and freed when the `for` block exits — one allocation for the entire loop, rebound to the next element each iteration |
| `mol` (built-in function) | **Static** | Pre-declared before program execution; always visible |
| List values, compound objects, reaction objects | **Implicit heap-dynamic** (Sebesta §5.4.3) | Managed internally by the runtime — not *explicit*-heap-dynamic in Sebesta's sense, because ANS exposes no `new`, no `delete`, and no pointers |

ANS deliberately has **no explicit-heap-dynamic storage**. There are no pointers, no `new`/`delete`, and no aliasing. This eliminates an entire class of reliability errors (use-after-free, double-free, dangling pointers) — a direct consequence of prioritising reliability over flexibility, as stated in §4.1.
